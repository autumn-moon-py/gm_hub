# 战斗模块设计草案

> 日期：2026-05-11
> 状态：设计草案，待审阅

## 背景

当前项目未来将作为单项目、多模式的产品容器存在。现有场景模式负责舞台、图层、音频与输出控制；本次新增的战斗模块不是场景模式下的附属小面板，而是一套与场景模式并列的独立模式壳。

本阶段的目标不是做一个强规则裁判器，而是做一个偏主持效率和玩家展示体验的半自动导演台。战斗模块需要和现有项目共享外层程序、共享底层资源，但在主持端和玩家端都拥有自己的独立工作壳与展示合同。

## 目标

- 在现有项目中引入与场景模式并列的 `battle shell`。
- 保持外层项目宿主最小但明确，承担项目级 chrome。
- 为主持端提供一套围绕战斗调度的独立工作区。
- 为玩家端提供一套固定战斗 HUD，而不是高配置输出编辑器。
- 复用现有输出窗口与流消息体系，避免另起一套平行输出管道。
- 让战斗资源、默认编成与当前战斗形成清晰分层。

## 非目标

- 第一版不锁定具体规则体系。
- 不做强规则裁判器。
- 不做多场战斗列表。
- 不做战斗历史系统。
- 不做战斗布局预设库。
- 不在战斗模式内内置背景/音频小控件。
- 不把场景图层直接建模成跨模式共享角色身份。
- 不让玩家输出完全等同于主持端当前页面。

## 总体架构

### 项目层关系

- 一个 `.gmh` 项目承载多个并列模式子系统。
- 场景模式与战斗模式属于并列关系，弱共享，不围绕场景模式单核生长。
- 外层程序壳共享，模式内完整换壳。

### 外层宿主与模式壳

采用分层处理：

- 外层宿主掌管项目级 chrome。
- 模式壳掌管模式级 chrome。

外层宿主是最小项目壳，固定保留：

- 项目标题
- 保存/打开
- 模式切换
- 输出窗口控制

切入战斗模式后，主体区域整体交给 `battle shell`。`scene shell` 和 `battle shell` 不是同壳切 tab，而是两套不同主持壳。

## 运行态模型

### 主持端页面状态与玩家输出状态分离

主持端当前在哪个页面，与玩家当前正在看什么，不是同一个状态。

更准确的状态拆分为：

- 主持端有当前工作页面/工作壳状态
- 战斗模块有准备态 / 已上屏态
- 玩家输出是运行时状态，不完全等同于主持端当前页面

### 战斗展示状态

- 战斗模式存在“准备态 / 已上屏态”。
- 进入战斗模式后，主持端可以先进入战斗工作区，但玩家窗口仍保持原场景画面。
- 当用户明确点击“开始展示战斗”后，玩家窗口才切到战斗界面。
- “退回准备态”是明确按钮动作，不是返回页面自动触发。
- 若战斗已经上屏，而主持端离开战斗页面但未退回准备态，玩家窗口继续保持战斗画面。
- 项目关闭或下次重开时，不恢复“玩家当前正在看战斗”的输出态。

## 场景模式与战斗模式的边界

### 共享内容

- 共享底层资源，例如图片、音频。
- 当前场景为战斗模式提供背景、音频与素材来源窗口。

### 不共享内容

- 场景中的玩家/NPC 图层不是战斗对象本身。
- 不建立项目级统一角色身份层。
- 场景图层只是视觉表现，不是跨模式共享的角色实体。

### 当前场景与当前战斗的绑定规则

- 当前战斗绑定项目当前选中场景。
- 场景切换时，当前战斗立即切换场景上下文。
- 切场景不需要确认弹窗。

切场景时只改变：

- 背景
- 音频
- 从当前场景辅助创建战斗资源时的素材来源

切场景时不改变：

- 当前战斗中的参战对象
- 行动顺序
- 前台
- 状态
- 备注

### 背景与音频联动

- 战斗模式对背景与音频采用持续活链接，而不是开场快照。
- 持续联动只到背景和音频为止。
- 战斗中若要修改背景/音频，允许返回主场景区自行切换，不在战斗模式内做内置控件。

## 四层模型

战斗模块拆为四层：

1. 资源层
2. 战斗资源库层
3. 默认战斗编成层
4. 当前战斗工作区层

各层关系如下：

- 资源层 -> 战斗资源库：活引用
- 战斗资源库 -> 默认战斗编成：强引用
- 默认战斗编成 -> 当前战斗：只在新建/重建当前战斗时展开
- 战斗资源库 -> 当前战斗：基础资料半同步
- 当前场景 -> 当前战斗：只影响舞台上下文和辅助创建来源

## Battle Shell 信息架构

`battle shell` 采用顶部主导航，包含三个一级页：

- 当前战斗工作区
- 默认战斗编成
- 战斗资源库

默认战斗编成是独立一级页，不挂在其他页之下。

## 默认战斗编成

- 默认战斗编成独立维护，不是当前战斗的自动镜像。
- 默认战斗编成条目对资源库对象采用强引用。
- 修改默认编成不会自动影响当前战斗。
- 默认编成只影响“新建/重建当前战斗”。
- 新建/重建当前战斗更接近“半成品进入”，而不是完全从空开始。

## 当前战斗工作区

### 结构

主持端战斗工作区采用以下布局：

- 左侧：行动顺序列表
- 中心：玩家视角近似预览
- 右侧：选中对象驱动的战斗辅助面板
- 下层：资源快捷入口 + 参战对象总表

### 中心预览与运行态按钮

- 主持端中心区域优先承担玩家视角近似预览。
- 该预览是玩家视角检查器，不是精确编辑器镜像。
- `开始展示战斗 / 退回准备态` 放在中心预览区上方。
- 这组按钮语义上属于“当前给玩家看的内容控制”，不并入左侧流程区或右侧辅助面板。

### 左侧行动顺序列表

- 左侧只放行动顺序列表。
- 行动顺序不自动生成，用户全程手动控制。
- 玩家和 NPC 可在同一条顺序列表里混排。
- 玩家对象也可以成为当前行动者。
- 主持端大部分选中动作倾向从左侧顺序列表发起，而不是从中心预览点选。

### 下层双区

页面下层采用左右双区，而不是上下分区：

- 左侧偏编成入口与补充入口
- 右侧偏当前战斗对象总表

左侧区域：

- 两种职责都保留，但默认编成为主
- 既承担从默认编成快速补充到当前战斗
- 也保留战中临时增援入口

右侧对象总表：

- 默认至少按 `玩家 / NPC` 分组显示
- 允许切换成单表视图
- 组内默认尊重手动整理顺序
- 系统默认不按当前行动者、前台或关键状态自动顶置

## 右侧战斗辅助面板

### 未选中任何对象时

- 默认显示明确空态，而不是战斗总览态
- 文案引导用户先选择对象
- 可保留少量快捷入口：
  - 从下层添加对象
  - 打开默认编成
  - 打开资源库

### 选中 NPC 时

第一屏必须包含：

- 基础信息
- 快速改值
- 状态与标记
- 骰子入口
- 外部结果回灌
- 战斗备注

采用顺序：

`基础信息 -> 快速改值 -> 状态与标记 -> 骰子入口 -> 外部结果回灌 -> 战斗备注`

说明：

- 该顺序采用身份信息优先
- 在 NPC 面板里，系统内骰子入口优先于系统外结果回灌入口

### 选中玩家对象时

玩家对象面板是 NPC 面板的轻量版：

- 没有 HP 区
- 没有关键加值区
- 没有骰子入口
- 保留基础信息、状态与标记、战斗备注

采用顺序：

`基础信息 -> 状态与标记 -> 战斗备注`

## 骰子区与结果回灌

### NPC 与玩家的边界

- 对 NPC 行动，战斗模式里可以直接投骰
- 对玩家行动，不在系统里发起投骰

因此：

- 骰子区主要服务 NPC
- 玩家行动主要在系统外判定

### 玩家行动结果回灌

- 玩家行动虽不在系统内投骰，但结果要能回灌到系统。
- 第一版以单目标为主，但预留多目标扩展位。
- 外部结果录入最少关注：
  - 命中结论
  - 公开结果文本

`HP` 改值不并入结果录入器，而是走右侧面板里的独立数值操作链。

## 战斗资源库

### 结构

独立 `战斗资源库` 页采用资源管理器式三栏结构：

- 左侧分类
- 中间列表
- 右侧详情编辑

左侧分类栏第一版只做到对象类型颗粒度：

- `NPC 库`
- `玩家展示对象库`

不做更细分类。

### 中间区

- 第一版采用资源卡片墙，不用高密度表格列表
- 卡片采用极简展示：大缩略图 + 名称
- 第一版不内置搜索或筛选入口
- 保持纯浏览式入口

### 右侧详情编辑区

- 采用即时保存
- 条目字段修改后直接写回
- 不引入显式保存按钮

### 主动作分配

- 左侧负责切分类
- 中间工具条负责当前分类下的主动作
- 右侧负责选中后的详情编辑

资源库页主创建入口明确偏向 `NPC`，不再要求与玩家展示对象保持完全对称。

## 从场景素材辅助创建战斗资源

### 通用规则

- 支持纯手动创建，也支持从现有场景素材辅助创建，整体倾向混合
- 辅助创建默认只看当前场景
- 不看全项目，也不是最近使用
- 选择器列出的内容是当前场景中的图层项
- 不是先图层再素材的两段式选择器
- 从当前场景图层辅助创建时，系统自动带入图层名称
- 其他字段不自动猜
- 最终绑定的仍然是素材文件，而不是图层实例

### 玩家展示对象

- 第一版基本不需要手动创建
- 可直接引用现有图层资源
- 名称默认使用图层名作为来源
- 资源库阶段不强调编辑运行时字段
- 备注与标记属于实例运行时信息，不在此阶段编辑

玩家展示对象从当前场景图层引用进资源库的主入口放在独立 `战斗资源库` 页内，并位于 `玩家展示对象库` 分类下的中间卡片区工具条。

### NPC

- `NPC` 的主创建入口放在 `NPC 库` 分类下的中间卡片区工具条
- `NPC` 立绘绑定同时保留两条路径：
  - 从项目资源里选
  - 从当前场景辅助带入
- 其中从项目资源里选是主编辑入口，从当前场景辅助带入是快捷入口

## 数据建模

### NPC 模板层

- 名称
- 立绘绑定
- 特性文本
- 默认最大 HP
- 默认关键加值

特性文本采用多行描述字段，定位为主持参考说明。第一版允许多行输入，但控制为短段落，不把它扩展成完整资料页。

### NPC 实例层

- 当前 HP
- 本场状态/标记
- 本场备注
- 是否当前前台展示
- 是否当前行动者

### 玩家模板层

- 名称
- 立绘绑定

当前理解中，玩家模板层第一版更接近轻量引用对象，而不是需要完整手工维护的模板实体。

### 玩家实例层

- 阵营/位置
- 本场备注
- 本场状态/标记
- 是否当前前台展示
- 是否当前行动者

### 字段拆层原则

- `NPC` 的模板层保存最大 HP
- `NPC` 的实例层保存当前 HP
- 关键加值不拆层，第一版视为模板固定值
- 玩家状态/标记视为纯实例态

### 多实例 NPC

- 同一个 `NPC` 模板可以在一场战斗中生成多个独立实例
- 命名规则：模板名 + 序号
- 例如：`史莱姆 1 / 史莱姆 2 / 史莱姆 3`
- 模板改名后，实例前缀也跟着变

## 资源库更新对当前战斗的影响

### 半同步范围

当前战斗对资源库基础资料采用半同步。当模板发生以下改动时，当前战斗中的实例默认自动同步：

- 名称
- 立绘绑定
- 特性文本
- 默认最大 HP
- 默认关键加值

### 最大 HP 同步规则

由于 `HP` 已拆成模板最大 HP 与实例当前 HP，因此最大 HP 变更采用条件式同步：

- 当前战斗实例同步新的最大 HP
- 若实例原本满血，则当前 HP 同步成新的满血
- 若实例原本已受伤，则保留当前 HP
- 若当前 HP 超出新的最大值，则向下截断到新的最大值

## 战斗对象状态与前台规则

### 状态类型

第一版至少区分：

- 候场
- 参战中
- 前台展示中
- 已退场
- 已失效

### 状态迁移原则

- 第一版状态切换近乎自由
- 不做严格规则状态机
- 主持端可以随时把对象改到想要的状态

### 前台与当前行动者

- 平时前台位可手动指定
- 但在行动者切换时，系统要强切前台
- 因此前台位不是绝对自由，当前行动者切换对前台有强制影响

## 玩家端固定战斗 HUD

### 输出合同

- 玩家端第一版采用固定战斗 HUD
- 不做高配置输出编辑器
- 主持端中心区对应的是该 HUD 的近似预览

### 视觉结构

- 以前台角色双核心为主视觉结构
- 双方前台立绘是主焦点
- 其他信息围绕前台区组织

### 流程信息挂接

- 当前行动者以贴附在对应前台角色上的强提示呈现
- 下一位行动者用顶部或侧边轻量信息条呈现
- 两者不抢同一视觉层级

### 角色附近 HUD

- 战斗 HUD 本身承担贴近角色头像/立绘附近的战斗信息层
- 公开结果不在角色附近 HUD 中承担
- 角色附近 HUD 第一版走纯状态型
- 轻事件信息以动画形式展现，不塞进角色常驻 HUD
- 常驻最小集为：名称 + 状态/标记

### 公开结果区

- 战斗公开结果直接复用主场景现有的骰子/输出区
- 不在战斗 HUD 中另做一块独立公开结果区

### 玩家固定可见层

- 双方前台立绘
- 当前行动者
- 下一位行动者
- 玩家对象状态
- 受击提示
- 结果文本区（复用主场景现有输出区）

### 默认不公开的信息

- NPC 状态
- NPC 当前 HP
- 完整行动顺序
- 战斗备注

## 动画与动态提示

用户明确非常在意以下三类动态反馈：

- 前台切换
- 受击提示
- 当前行动者提示

第一版采用混合模型：

- 主体画面由状态决定
- 动态提示和动画由事件驱动

整体目标不是追求很绚丽的大动画，而是让这些关键反馈必须存在并可感知。

## 实时性原则

- 战斗模式是实时导演台
- 主持端一改，玩家窗口立刻同步
- 不做明显的草稿态 / 发布态
- 但“玩家输出是否正在展示战斗”这件事本身，仍由明确按钮控制

## 风险与边界

- 资源库卡片墙第一版不做搜索筛选，后期资源规模变大后可能需要补充定位能力
- 玩家展示对象第一版被刻意压成轻量引用对象，后续如果战斗规则要求更多模板字段，需要重新扩展建模
- `NPC` 特性文本第一版虽然允许多行，但若后续被滥用为大段资料页，可能会压迫右侧详情编辑体验

## 设计总结

这套设计把战斗模块定位成现有项目里的第二套独立模式壳：

- 外层宿主最小化，只负责项目级 chrome
- `battle shell` 内部再拆成工作区、默认编成、战斗资源库三页
- 工作区围绕导演调度而不是规则裁判展开
- 玩家端采用固定 HUD，但公开结果继续复用现有输出区
- 资源库和默认编成为当前战斗提供稳定来源，形成清晰的分层关系

整体优先级始终是：主持效率、清晰分层、玩家展示体验。
