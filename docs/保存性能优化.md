# 保存性能优化(归档)

> 本文档记录新格式 `.gmh`(ZIP 内嵌资源)保存耗时过高问题的排查与修复过程,记录最终实现状态(截至 2026-08-16)。

## 一、背景与问题现象

用户反馈"保存速度慢",点击保存到提示「保存成功」需要 3-10 秒。实测确认:

- 慢的场景为**新格式**(formatVersion=2,ZIP 内嵌资源)项目
- 旧格式(gzip 老项目,资源不内嵌)保存仅 30-60 ms,无性能问题

## 二、排查过程

### 2.1 添加耗时日志

在保存链路各环节插入 `[保存耗时]` 前缀计时日志,覆盖:

- `ProjectController.saveProject`(controller 层总计,含输出窗口同步调度)
- `_saveNow`(store 层总计,含资源总大小统计)
- `ProjectFileService.saveProject` / `_writeZip` / `_writeProjectFile`(ZIP 打包、序列化、写盘分段计时)
- `_syncOutputWindow`(保存后输出窗口同步耗时与 payload 大小)

### 2.2 实测数据(修复前)

测试项目:冰封之爱的囚徒,20 个内嵌资源,资源总大小 80691 KB:

| 环节 | 耗时 | 说明 |
|------|------|------|
| ZIP 打包 | 6269 ms | 全量压缩所有资源 |
| 写盘(flush) | 88 ms | 正常,非瓶颈 |
| **保存总计** | **6359 ms** | 与用户体感一致 |

关键对比:资源 80691 KB,压缩后产物 79991 KB,**压缩收益仅 0.9%**,却消耗 6.2 秒 CPU。

## 三、根因

`ProjectArchiveService.buildBytes` 中 `ZipEncoder()` 默认对**所有条目**做 deflate 压缩,包括资源条目:

- 图片(PNG/JPG)与音频(MP3)本身已是压缩格式,ZIP 再压收益几乎为零
- 全量压缩 78 MB 已压缩数据纯属空耗 CPU,是保存耗时的绝对主体
- 旧格式不内嵌资源,故无此问题;新格式资源越多,保存越慢

次要因素(非瓶颈,未处理):`Isolate.run` 跨 isolate 复制整个资源字节表、CRC32 校验计算、内存中 Archive 组装。

## 四、修复方案

`lib/src/store/project_archive_service.dart` 的 `buildBytes`:

```dart
// 资源(图片/音频)本身已是压缩格式,ZIP 再压收益极小,直接 store 避免空耗 CPU
assetMap.forEach((name, bytes) {
  archive.addFile(ArchiveFile(
    name,
    bytes.length,
    bytes,
  )..compress = false);
});
```

- 资源条目 `ArchiveFile.compress = false`,走 ZIP store 模式(不压缩,仅计算 CRC32)
- `manifest.json` / `project.json` 文本条目保留 deflate 压缩(体积小,开销可忽略)
- 改动仅一处,`buildBytesInIsolate`、`ProjectArchiveService.write`、迁移路径自动受益

## 五、验证记录

### 5.1 实测数据(修复后)

同一项目,同一保存路径:

| 指标 | 修复前 | 修复后 | 提升 |
|------|--------|--------|------|
| ZIP 打包 | 6269 ms | 767 ms | 8.2 倍 |
| 写盘(flush) | 88 ms | 87 ms | 不变 |
| **保存总计** | **6359 ms** | **856 ms** | **7.4 倍** |

- 资源 80691 KB 打包后 80695 KB,仅增大 4 KB,store 模式对已压缩格式零损失
- 文件可正常读取:ZIP 解码器对 store 条目按 `compressionMethod` 分流,直接读原始数据

### 5.2 兼容性

| 项 | 结论 |
|----|------|
| 新格式重开 | 兼容,store 条目正常解析 |
| 跨格式互读 | 不受影响,ZIP 容器格式未变 |
| 文件大小 | 增加约 0.9%(已压缩资源无压缩收益,属预期) |

## 六、遗留项(不在本期范围)

- **资源脏标记增量打包**:只打包本次变更资源,未变更资源复用上次 ZIP 字节,可进一步将保存压至几十 ms 量级——改动中等,本期不做
- **耗时日志保留**:`[保存耗时]` 日志保留用于后续监控,保存变慢时可直接定位环节
