# .gmh 项目文件资源内嵌化(归档)

> 本文档由原设计文档(2026-08-08-gmh-asset-embedding-design.md)与实现计划(2026-08-08-gmh-asset-embedding.md)整合而成,记录最终实现状态(截至 2026-08-16,含代码审查与修复记录)。

## 一、背景与目标

原 `.gmh` 项目文件只包含 JSON 元数据,图片与音频资源以**绝对路径**存放在 `NodeModel.asset`、`AudioTrackModel.asset`、`BattleResourcePortraitBinding.asset` 字段中,运行时直接读磁盘。问题:

- 项目文件无法脱离源机器分发,拷到其他机器后资源全部丢失
- 用户移动/重命名原始资源后,项目打开全部显示为占位符
- 没有"项目"概念边界,实质是"元数据 + 资源索引"

目标:资源二进制内嵌进 `.gmh` 文件,真正自包含、可分发;同时支持老格式一键迁移。

## 二、文件格式规范

### 2.1 ZIP 容器结构

新格式 `.gmh` 为标准 ZIP(DEFLATE 压缩):

```
example.gmh              # ZIP 容器
├── manifest.json            # 格式元信息
├── project.json             # 项目 JSON(asset 为 ZIP 内相对路径)
└── assets/                  # 资源目录
    ├── img_<sha256前8位>.png
    └── audio_<sha256前8位>.mp3
```

### 2.2 manifest.json

```json
{ "formatVersion": 2, "toolName": "GM Hub", "toolVersion": "1.0.0", "createdAt": "..." }
```

`formatVersion: 2` 为唯一版本标识;`toolVersion` 取自 `ProjectArchiveService.kToolVersion` 常量(与 pubspec.yaml 同步维护)。

### 2.3 project.json

与 `ProjectModel.toPrettyJson()` 输出一致,唯一变化:所有 `asset` 字段由绝对路径改为 ZIP 内相对路径(`assets/...`)。

### 2.4 assets 命名与去重

- 图片:`img_<sha256前8位>.<原扩展名>`
- 音频:`audio_<sha256前8位>.<原扩展名>`
- battle 立绘复用 `img_` 前缀
- 基于内容哈希命名,同源资源多次引用天然去重

### 2.5 格式识别

`ProjectFileService._detectFormat` 按文件头 4 字节判断:

| 魔数 | 格式 |
|------|------|
| `50 4B 03 04` (PK) | ZIP(新格式) |
| `1F 8B` | gzip + JSON(老,压缩) |
| `7B` (`{`) | JSON(老,明文) |
| 其它 | 无法识别,返回空项目(fallback) |

老格式运行时兼容保留,已存在的项目继续以老格式打开,直到用户主动迁移。

## 三、架构设计

### 3.1 新增模块

| 文件 | 职责 |
|------|------|
| `lib/src/store/asset_resolver.dart` | `AssetResolver` 抽象 + `LegacyAssetResolver` / `EmbeddedAssetResolver` 实现 |
| `lib/src/store/project_archive_service.dart` | ZIP 读写;`buildBytesInIsolate` 在 isolate 中构建 ZIP 字节 |
| `lib/src/store/asset_cache_service.dart` | 缓存目录管理:解压、失效判定、完整性校验 |
| `lib/src/store/project_migrator.dart` | 老格式迁移:引用收集、缺失检测、读字节、重链 |

### 3.2 关键改动

- **ProjectFileService**:`loadProject` 返回 `ProjectLoadResult(model + resolver + assetMap)`;`saveProject` 按 `formatVersion` 分流(v2 走 ZIP,否则 gzip/明文);v2 同步保存 `saveProjectSync` 抛断言防误用
- **ProjectStore**:持有 `_assetResolver` 与 `_assetBytes`;`_pruneUnusedAssets` 按引用清理无资源字节(含 undo 栈与 battle 立绘保护);`_resolveAssetAbsolutePath` 全部委托 resolver
- **运行时字节同步**:导入/替换/重链资源在 v2 分支读字节 → `_newAssetKey`(SHA256 命名)→ `_syncAssetBytes`
- **undo 语义**:快照收窄为 root-only,并记录 `assetRefs` 供 prune 保护;音轨/audioState/battle 不再随 undo 回滚

### 3.3 运行时数据流

```
导入/替换/重链 → _assetBytes 同步 → prune 清理无引用字节
→ 保存(ZIP,Isolate.run 压缩)→ 重开(魔数识别)→ ZIP 解析
→ 缓存命中/重新解压 → EmbeddedAssetResolver → 显示/播放
```

所有 `Image.file` / `DeviceFileSource` 路径经 `_resolveAssetAbsolutePath` 委托 resolver:

| 格式 | resolver | 实际磁盘路径 |
|------|----------|--------------|
| 新 | `EmbeddedAssetResolver(cacheDir)` | `%APPDATA%/gm_hub/project_cache/<hash>/assets/...` |
| 老 | `LegacyAssetResolver(projectDir)` | 原绝对路径,或 projectDir + 相对路径 |

### 3.4 缓存设计

- 位置:`%APPDATA%/gm_hub/project_cache/<sha256(规范化路径,统一小写)>/`
- 结构:`project.json`(调试副本)+ `assets/` + `.gmh_cache_meta`(sourcePath/sourceMtime/sourceSize/extractedAt)
- 失效:三重校验(path + mtime + size)+ assets 目录存在性;meta 最后写入,中途崩溃可自愈重建
- 读取:每次打开均全量解析 ZIP 到内存 `assetMap`(保存需要),缓存仅省去写盘

## 四、迁移流程

菜单「转换为新版本格式」(`convertToNewFormat`):

1. 收集引用:`collectAssetRefs` 递归 root 图片节点 + 音轨 + battle 立绘
2. 归一化:相对路径按项目目录解析为绝对路径(避免相对进程 cwd 误判)
3. 缺失检测:`File.existsSync` 列出丢失项,弹窗提供「跳过并迁移 / 取消」
4. 读字节:isolate 中执行,单文件读取失败仅置空该引用不阻断整体
5. 重链:SHA256 命名生成 `assets/*`,`oldToNew` 映射替换 model 中所有 asset,`formatVersion = 2`
6. 备份:原文件复制为 `.gmh.bak`
7. 写 ZIP:`buildBytesInIsolate` + 异步写盘
8. 重载:解压缓存 + 注入 `EmbeddedAssetResolver` + 刷新 store
9. 失败回滚:任一环节失败从备份恢复原文件

全程 `runWithGlobalLoading` 遮罩,防止迁移期间用户操作被快照覆盖。

## 五、健壮性与安全

- **Isolate 陷阱**:`Isolate.run` 闭包必须置于静态方法内且只捕获纯数据参数,否则会连带捕获 `ProjectStore`(含 AudioPlayer 的 `_AsyncCompleter`)导致 unsendable 错误——统一走 `ProjectArchiveService.buildBytesInIsolate` 静态入口
- **路径穿越防护**:ZIP 条目名含 `..` 一律丢弃(收集层 + 写盘层双重校验);`EmbeddedAssetResolver` 对含 `..` 的相对路径返回 null
- **日志**:迁移开始/完成/失败/恢复、缺失资源列表、单文件读取失败、ZIP 解析失败、越界条目均打印,便于排查
- **异步化**:ZIP 构建、文件读写、缓存解压、导入读字节均不阻塞 UI 线程
